# TC-CSRF-01: Cross-Site Request Forgery — Profile Email Change

## Identifier
TC-CSRF-01

## Objective
Verify whether the profile email-change functionality
(`/profile/update`) is vulnerable to CSRF, using a genuinely
cross-origin proof-of-concept page (not a same-origin request or a
locally opened file), to realistically demonstrate that an
attacker-controlled website — entirely outside this application's
control — can force a state-changing action on behalf of an
authenticated victim.

## Preconditions
- Application running locally on port 5000 (`flask run`).
- Simulated attacker server running locally on port 8080
  (`python docs/testing/attacker_server.py`), serving
  `docs/testing/attacker_site/index.html`.
- Tester (acting as the victim) logged in as a normal user in one
  browser tab.

## Test Environment
- Branch under test: `vulnerable` (baseline) and `secure` (post-fix
  verification)
- Tool: two local HTTP servers (lab app + simulated attacker site),
  browser (manual)

---

## Sub-scenario A — Baseline: legitimate email change (control test)

**Action:** Log in, navigate to `/profile`, submit the email-change
form with a new address.

**Expected result:** Email is updated; `/profile` reflects the new
value.

**Actual result (vulnerable branch):** As expected.

**Actual result (secure branch):** As expected — no regression (the
legitimate form now also submits a valid CSRF token automatically,
generated by the server for this session).

---

## Sub-scenario B — Cross-origin forged request

**Setup:**
1. Victim logs into the lab app (port 5000) in Tab 1, confirms
   current email on `/profile`.
2. Victim opens a **new tab** and navigates to
   `http://127.0.0.1:8080` (the simulated attacker site) — note this
   is a genuinely different origin (different port), not a local
   file or a page served by the lab app itself.
3. The attacker page displays a disguised "You've won a prize!"
   message. On load, a hidden form (targeting a hidden iframe, so
   the visible page does not navigate away) automatically submits a
   POST request to `http://127.0.0.1:5000/profile/update` with
   `email=hacked-by-csrf@attacker.com`.
4. Victim switches back to Tab 1 and reloads `/profile`.

**Expected result (vulnerable branch):** Because the browser
automatically attaches the lab app's session cookie to any request
targeting `127.0.0.1:5000` regardless of which page initiated it,
and because `update_email()` performs no check beyond "is a valid
session cookie present," the forged request is processed as if it
were legitimate.

**Actual result (vulnerable branch):** **Confirmed.** The email on
`/profile` changed to `hacked-by-csrf@attacker.com` without the
victim ever interacting with the lab app's own `/profile` form
during this step — confirmed via curl simulation with real
`Origin: http://127.0.0.1:8080` and `Referer: http://127.0.0.1:8080/`
headers, matching what the browser sends in the actual attack.

**Actual result (secure branch):** The forged request is rejected
with **HTTP 400 Bad Request**, response body: *"The CSRF token is
missing."* The victim's email remains unchanged. The attacker page
has no way to obtain a valid `csrf_token` value, since that value is
generated server-side per session and only embedded in the
genuine `/profile` page's own form — a page the attacker's site never
loads or has access to.

---

## Sub-scenario C — Confirming the fix does not rely on Origin/Referer alone

**Action (secure branch):** Repeat the forged request via curl, but
this time additionally omit the `Origin` and `Referer` headers
entirely (simulating a stricter attacker who scrubs those headers, or
a browser configuration that omits them).

**Expected result:** The request should still be rejected — CSRF
protection here is based on possession of a valid, unpredictable
token tied to the session, not on inspecting request headers that an
attacker may be able to spoof or a privacy-focused browser may strip.

**Actual result (secure branch):** **Confirmed.** Request rejected
identically with HTTP 400, "The CSRF token is missing," regardless of
Origin/Referer header presence.

---

## Overall Conclusion

The `vulnerable` branch's `/profile/update` endpoint is exploitable
via CSRF: an attacker-controlled page, hosted on a completely
separate origin with no relationship to the lab application, can
silently force an authenticated victim's browser to change their
email address, relying solely on the browser's automatic cookie
attachment behavior.

The `secure` branch's fix — enabling Flask-WTF's `CSRFProtect`
application-wide and embedding a per-session `csrf_token` in every
state-changing form — closes this attack path. The protection is
token-based rather than header-based, making it robust even against
attackers who control request headers, which a purely
Origin/Referer-checking defense would not be.
